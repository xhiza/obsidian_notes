### L3-4465 troubleshooting huddle

Participants: [[Torsten Kilias]], [[Thomas Uebensee]], [[Stefan Reich]], and [[Edis Shabi]].

- Investigated a database that failed after an update. The database was on the older `8.29.10` release and used the legacy split SLC mechanism.
- Found an empty/old SLC directory that appeared to interfere with startup. The directory was moved aside, after which the main database started successfully and the expected language-container parameters appeared in the logs.
- The working hypothesis is a timing/configuration problem during upgrade: `C4`/database configuration may run before the new SLCs are fully unpacked, causing stale or incomplete local configuration to be selected.
- The error investigated was related to being unable to find a valid root path for an SLC while reading the SLC configuration bucket. The issue may be limited to a worker cluster or a specific node; logs for worker clusters were not readily available.
- Worker clusters initially did not show the current parameters even though the update reported success. Running `DB CONFIGURE` for the worker-cluster entries refreshed them to the new version.
- After refreshing the configuration and restarting the relevant processes, the database and worker clusters appeared online with the correct parameters. No further startup error was observed.

Follow-up:

- Update L3-4465 with the findings and the current working state.
- Collect and review logs to determine why worker-cluster parameters were not updated despite `DB CONFIGURE` reporting success.
- Investigate whether the upgrade process needs to wait for SLC unpacking before running configuration, and perform a root-cause analysis next week.
- Customer-facing update can state that the database was restored and is ready for testing; the underlying cause remains a suspected upgrade timing/configuration race.
